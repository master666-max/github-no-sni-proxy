GitHub 无SNI反代 —— 使用说明
============================================================

【这是什么】
一个纯用户态的小代理，监听本机 127.0.0.1:443。
浏览器访问 github.com 时流量先到它，再由它去连 GitHub。
它做了一件关键的事：连 GitHub 时「不发 SNI」，从而绕过 GFW 对
github.com 的封锁。

它不装任何内核驱动，360 不会拦它（对比 FastGithub 用 WinDivert，
在本机被 360 主动防御挡死，报 Win32Exception 1243）。


【怎么用】
1) 双击「一键部署.bat」，同意管理员权限
   它会自动完成：备份 hosts → 装私有 CA 到系统信任区 → 写 36 个域名映射
                  → 刷新 DNS → 后台把反代拉起来
2) 完全退出 Edge（任务栏图标右键 → 关闭所有窗口），再重新打开
3) 访问 https://github.com

可选：想开机自动运行，双击「开机自启.bat」，注册一个计划任务，
      以后登录 Windows 自动起代理、不弹 UAC。反悔就跟部署一起卸掉。

想彻底还原：双击「一键卸载.bat」，进程/hosts/CA/自启任务一起清干净。


【文件都是干嘛的】
  一键部署.bat    装好一切并启动反代（自动提权）
  状态监控.bat    ★ 双击弹出状态监控窗口（不要求管理员权限，部署前后都能看）
  开机自启.bat    可选，注册开机自启
  启动反代.bat    手动前台启动，窗口里能看实时日志，关窗即停
  一键卸载.bat    全部还原
  status_gui.py   监控窗口本体（纯标准库 tkinter，零依赖；python status_gui.py --selftest
                  可无头自检，不弹窗）
  selftest.py     自检：不装任何东西，进程内直接跑。
                  python selftest.py -A  = A 段离线单测 159 项 + C 段本地端到端 4 项
                                           （都不联网，约 12 秒）
                  不加参数 = 再连真实 GitHub 跑 B 段全量（约 70 秒）。
                  全量会校验**内容**（HTML/JSON/图片/zip 魔数），不只看字节数。
                  C 段是「真 git push 穿真反代」：真 TLS 服务端 → 真 handle/serve
                  → 真 git-http-backend，最后回裸仓库核对提交与大文件字节数。
  deploy.py / undeploy.py / gh-proxy.py / run-proxy.cmd   脚本本体
  certs/          证书目录。ca.key 是私有 CA 私钥，只在本机，别外传


【状态监控窗口能看什么】
· 五个状态卡：反代进程（PID + 是否真活着，PID 会被系统复用所以要核对）/
  端口 443 有没有在听 / hosts 映射 36 个域名的覆盖数 / 私有 CA 是否还装在
  系统信任区 / 近 1 分钟请求数（从日志统计）
· 全链路测试：真发 HTTPS（SNI=域名、用我们的 CA 验签）走 127.0.0.1:443 ——
  这一条测的是「hosts + 反代 + 上游通道 + 证书」整条链，并校验内容特征
  （HTML / JSON / zip 的 PK 魔数 / 图片魔数），不是只看状态码。
  反代没在跑时会直接告诉你是「连不上 443」还是「证书验签失败」。
  可手动点，也可勾「每 60s 自动测」。
· 实时日志：tail gh-proxy.log（反代的所有请求都记在这）。
· 复制诊断信息：一键把全部状态 + 6 条链路测试结果压成文本进剪贴板，方便贴给我。
· 注意：监控窗口**不需要**管理员权限；它不会去改任何东西（只读）。


【为什么这个证书方案是安全的】
市面上不少 GitHub 加速工具（包括 FastGithub）用的是**公开分发**的 CA，
私钥人尽皆知。把它装进系统信任区，等于废掉浏览器的证书校验 ——
任何人拿到那对密钥，就能伪造任意网站的证书骗过你（银行、邮箱都算）。

本工具用的是**本机现场生成**的私有 CA：
  · ca.key 只存在 certs/ 里，从未离开这台机器
  · 服务器证书由它签发，并且带完整证书链，兼容 Windows schannel
  · 卸载时把这张 CA 从系统信任区删掉
（certs/fastgithub-ca.crt.bak 只是被替换掉的旧公开 CA 的留档，没有任何用途。）


【原理速查】
· 实测结论：对 github.com 发 SNI → TCP 超时；不发 SNI → 完整收到 57 万字节响应
· 所以链路是：浏览器 --TLS(SNI=github.com)--> 本代理 --TLS(不发SNI)--> GitHub
· 上游策略：先试「正常 SNI」（最正宗），全挂了才退回「不发 SNI」。
  注意 GFW 对 github.com 的封锁是**时松时紧**的，所以两套策略都留着。
· GitHub 的多个 IP 里常有一两个被黑洞（TCP 通、TLS 握手永不返回），
  所以每轮让 4 个 IP 并发竞速，谁先握手成功用谁，其余立刻丢弃
· 解析结果里出现已知的 GFW 污染 IP（如 59.24.3.173）会被自动剔除

【v2 内核怎么设计的】（对齐 RFC 9110 与 Go 的 httputil.ReverseProxy）
· 流式搬运，不整包缓冲：一个仓库 zip 几百 MB、git push 的 packfile 都能过，
  内存占用与文件大小无关。响应体 ≤1MB 时先攒着不发 —— 这样万一被截断，
  「一个字节都还没发给浏览器」，可以换条通道整包重试；超过 1MB 就边收边发。
· 上游连接池：打开一个 GitHub 页面要发几十个请求，复用 TLS 连接能省掉
  几十次握手，明显更快。空闲连接最多留 45 秒、每条最多复用 200 次。
· 严格剥 hop-by-hop 头（RFC 9110 §7.6.1）：Connection 里点名的字段先删，
  再删 Connection 本身；Keep-Alive/TE/Upgrade 一律不转发，响应侧的 Connection 同样处理。
  **唯一的例外是 Transfer-Encoding** —— 分块帧我们是原样中继的，剥掉声明就等于
  「有分块帧、无分块声明」，接收方会把块长（如 "16EC"）当正文，页面整页花掉
  （首页 577KB 全乱码踩过）。请求侧同理：chunked 请求体必须保留 TE 声明并丢掉
  Content-Length（RFC 9112 §6.3）。
  同时剥掉 alt-svc —— 否则浏览器会记住 HTTP/3 地址、绕过本代理直连。
· 专一：只服务 GitHub 域名。其它域名一律 403，防止本机别的程序把 443 当开放代理用。

【v2.1 补的三个隐蔽坑】（都踩到过，都有离线用例钉死）
· 「握手成功 ≠ 通道可用」要分**两个阶段**判：
  GFW 既可能「放行握手、把请求整个吞掉（连响应头都不回）」，
  也可能「放行响应头、再把响应体吞掉」。老代码只在「体传到一半」才惩罚这个 SNI 模式，
  于是重试会一次次重新选中同一条坏通道；实测 github.com 首页因此空耗 79 秒后回 502，
  而另一条通道 2 秒就能通。现在这两种都算通道级故障。
  （注意区分：池里捞出的连接等不到响应头，那只是死连接，不该牵连 SNI 模式。）
· **超时预算必须自洽 —— 单阶段等待不能把「重试」从结构上挤掉**：
  实测 GitHub 响应头 0.07~0.57s、体首字节 0.07~0.65s（连 linux 全量打包也只要 0.35s）。
  所以定成 等响应头 20s / 等体首字节 15s / 体停滞 12s，**每一个都明显小于重试总预算 45s**。
  ⚠️ 这条最反直觉：体首字节原先是 60s（理由是「服务端要现算」），比 45s 的总预算还长，
  结果**第一次尝试就吃光预算，重试在结构上不可能发生** —— 表现就是首页硬等 60s 后 502。
  离线用例里专门有「预算自洽性」断言，以后调参不会再犯。
· DNS 里会混进「不属于这个域名」的 IP：实测 20.205.243.166 挂在 github.com
  名下、也被 DNS 列为 api.github.com 的候选地址，可它**不认 api 这个虚拟主机** ——
  无论发不发 SNI，都回 `301 Location: https://github.com/<原路径>`。
  竞速一旦选中它，浏览器直接跳去 github.com 的 404 页。**静默错内容比 502 难查得多。**
  现在会识别这种「默认虚拟主机兜底」的回应（判据：3xx + Location 恰好把同一路径
  挂到 github.com 下），把该 IP 拉黑 10 分钟并换一条重试。
· 杀进程前先核对身份：pid 文件会过期，重启后 Windows 会把那个 PID 复用给别的
  进程，照着旧文件 taskkill 会误杀无辜。现在先查该 PID 的命令行里有没有
  gh-proxy.py，对不上就交给按命令行扫描的兜底逻辑。


【v2.2 第三轮全量审查：又挖出 6 个】（均有离线/端到端用例钉死）· **git push 的请求体一旦超过 http.postBuffer（默认 1 MiB），git 会改用
  `Transfer-Encoding: chunked`** —— 而老代码对**任何**带 TE 的请求一律回
  411 Length Required。也就是说「仓库大一点就推不上去」，且报错只出现在客户端，
  服务端只有一行 warn，极难归因。实测（git 2.55 + git http-backend）一次 3.1 MB 推送：
      POST /r.git/git-receive-pack   Transfer-Encoding: chunked   CL=None
  现在请求体的 chunked 分块帧**原样中继**（复用响应侧那个严格扫描器，
  请求与响应本来就是同一套 RFC 9112）。只有「最后一层编码不是 chunked」
  （如 `TE: gzip`）才回 501 —— 那种情况我们无法界定请求体到哪结束。
  C 段用例就是跑一次真的 3 MiB push，再核对远端对象与字节数。
· 客户端报文非法（分块帧乱）以前混进 UpstreamBroken：日志写「上游失败」
  （把排查方向整个带偏），客户端拿到 502（让它以为重试一下就好，于是把坏字节再送一遍）。
  现在单独一类错误 → **400**、不重试、日志如实说。
· **absolute-form 请求行必须改写成 origin-form**（RFC 9112 §3.2.2）：
  配了 http_proxy 环境变量的工具（curl / git 都会）会发
  `GET http://github.com/x HTTP/1.1`。原样转给上游等于把「用哪个虚拟主机」的决定权
  交给请求行里的 authority，与 Host 头打架时会被路由到别的 vhost、回一个 301；
  而那个 301 恰好长得像「答错虚拟主机」→ 把一个**好 IP** 拉黑 10 分钟。
  等于自己把最好的通道踢出竞速，且完全无从归因。
· 连接池的**孤儿桶**会泄漏 fd：池按 (host, ip, 模式) 分桶，而 pool_get 只查
  「当前 GOOD_PEER」那一个桶 —— GOOD_PEER 一换 IP 或换模式（拨号失败、模式惩罚都会），
  旧桶就再没人查询、也再没人做过期回收（过期检查在 pop 那一侧），
  里面的 socket 一直占着 fd 到进程退出。现在 pool_put 每请求顺手扫一遍、
  只保留当前 peer 的桶。
· **卸载脚本缺了 hosts 安全闸**：读出空内容但文件非空（编码/权限异常）时，
  has_block 会变成 False，于是退化成「拿首次部署时的备份覆盖当前 hosts」——
  把部署之后所有改动一起抹掉。hosts 是系统文件，这种覆盖不可逆。
  现在 deploy / undeploy 共用同一条判据，宁可中止。
· `BODY_STALL_TIMEOUT` 被重复定义了两次（连注释都不一样），已合并。


【v2.3 部署后才会现形的致命 bug：反代把自己当上游】（2026-09-14 实测定位）
部署后 raw / avatars / gist 三个域必挂 502，而 github.com / api / codeload 正常。
根因是一条**部署前永远不会暴露**的链：
  · hosts 把我们服务的 36 个域名都指向 127.0.0.1（这正是它的作用）；
  · 而「解析上游 IP」原先是走 `getaddrinfo`，**系统解析器会读 hosts** ——
    于是「上游」被解析成了我们自己（127.0.0.1）；
  · 反代于是连上自己、把自己当上游，那一层再解析、再连自己……一路递归，
    每层吃掉一个并发槽（上限 128），最后「并发已满」→ 外层拿到 502，
    日志被 `[WinError 10053/10054] … 127.0.0.1: …` 刷屏。
  · 少数域名（github.com / api / codeload / gist）因为另有硬编码兜底 IP 才侥幸能通 ——
    这就是「为什么只有一部分域名坏」的答案。
  · **最阴的地方：没部署时 hosts 是干净的，DNS 正常，自测全绿、一切正常，一部署就现原形。**
修复（两道防线，都补了回归用例）：
  ① 解析层**不再依赖系统解析器**：直接对公共 DNS 发 UDP 查询拿真实 A 记录
     （223.5.5.5 为主，119.29.29.29 为辅；实测 1.1.1.1 在境内常超时，不采用），
     并统一过滤「污染地址 + 本机地址」；系统解析器只当兜底且必须剔掉本机地址；
     同时把兜底 IP 池补全到「部署后会用到的所有域名」（raw/avatars/objects/pages/
     githubassets/media/release-assets… 的 Fastly 段实测写死）。
  ② 拨号层红线：`dial()` 见到 127.0.0.1 / 0.0.0.0 / ::1 直接拒绝 ——
     这条路径以后就算被新代码绕过，也不会再发生自杀式递归。
  实测（同一条链，修前 → 修后）：raw 502 → **200 / 6KB / 250ms**；
  avatars 502 → **200 / 7.2KB / 241ms**；gist 502 → **200 / 315KB**。

【v2.3 第二处：某个 SNI 模式「整段握不上手」也要记惩罚】
实测 github.com 的「正常 SNI」会出现 4 个 IP 全部握不上手（TCP 通、TLS 无响应），
而「无 SNI」1 秒就通。原先把「整段失败」当无事发生，下次 GOOD_PEER 失效时又要
先白等一轮（6s × N），实测首页因此拖到 **23 秒**。现在整段失败的模式会被记惩罚
并排到队尾 —— 下次直接先试能通的那条。

【v2.4 抖动期延迟优化：别把时间浪费在已经被吞掉的通道上】
· **无体幂等请求（GET/HEAD）单独一套更短的头预算**（10s，而不是 20s）。
  实测（2026-09-15）github.com 的新建连接会「握手成功、请求被吞」，要连拨两次、
  每次等满 20s 才通 —— 总共 40s，浏览器和监控都先放弃了。
  这类请求重试是安全且几乎免费的，所以把预算压到 10s：
  实测头 TTFB 只需 0.07~0.57s（含 linux 全量打包），10s 是 17 倍余量，
  且 10+10+10=30s 仍远小于 45s 重试总预算 → 最坏从 40s 降到 ~20s。
  ⚠️ **带请求体的请求（POST / git push）不这么干**：上游收完大 pack 后真的可能
  算十几秒才回头，那时误杀比多等更糟，所以仍按 20s。
· **「真的跑通过请求」的模式会被优先选用**。原先挑 SNI 模式只看握手成败，
  而 GFW 恰好让握手永远成功、之后吞掉请求 → 惩罚完这条模式，下次竞速又按握手
  选回它，每次新建连接都交一次学费。现在额外记住「上次真的把请求跑通的是哪条模式」
  （MODE_GOOD）并优先用它；惩罚仍然优先于提升，所以坏了立刻会被压下去。

【监控窗口的两处改进（v2.4）】
· **客户端超时 10s → 30s**：反代自己的重试预算是 45s 量级，客户端只给 10s 必然
  把「还在重试」误报成「超时失败」（之前就把能通的 github.com / avatars 报成 ✗）。
· **超时的项自动再试一次**：GFW 抽风时第一次尝试常被整个吞掉，而那时该 SNI 模式
  已被记惩罚 —— 第二次通常几百毫秒就通。重试后成功会注明「第一次超时，第二次通」。
  另外成功但超过 8s 的会标「⚠慢」并注明是 GFW 抽风重试后才通，与真失败区分开。

【已知限制】
· GitHub 的阻断是**抽风式**的：同一目标换个时刻就通。所以单轮自测 5-7/7 属正常，
  失败项基本是网络波动，不是程序坏了。
· 走 **Fastly** 的那几个域（`raw.` / `avatars.`，整个 IP 段就是 185.199.108~111.133）
  在被针对时**会整段 TCP 超时**。此时 4 个 IP × 2 种 SNI 模式全都不通，
  代理没有可换的通道 —— 它会在 **12 秒内**干净地回 502 让你刷新（不会让你干等）。
  这是实测过的：同一时段 github.com / api / codeload / gist 都正常，只有这两个域不通。
· `gist.github.com` 最顽固：会被 DNS 污染（解析到 59.24.3.173 这类假地址）并被 RST。
· 别拿本代理去反复拉超大仓库 zip（如 linux 全量 zip）—— GitHub 会限流回 **429**。
  那与代理无关，歇几分钟即可。
· 反代必须保持运行。如果代理关了而 hosts 还指着 127.0.0.1，
  GitHub 会变成「连接被拒绝」（比原来的超时更难看）。停用请走「一键卸载.bat」。
· 如果还在用 Watt Toolkit(Steam++)，建议把它的 GitHub 加速关掉，
  避免两套改 hosts/代理的机制互相打架。

【CRL 分发 / 为什么 curl 会「无缘无故」打不开】
------------------------------------------------------------
（2026-09-21 新增。这是本项目踩过最隐蔽的一个坑。）

症状：
  curl: (35) schannel: next InitializeSecurityContext failed:
  CRYPT_E_NO_REVOCATION_CHECK (0x80092012) - 吊销功能无法检查证书是否吊销。

⚠️ 错误信息有误导性。它读起来像「CRL/OCSP 服务器连不上」，
   实际是**反代自己出示的证书压根没声明任何 CRL 地址** ——
   「没有东西可查」不等于「查不到东西」。两者修法完全不同。

⚠️ 而且**只有 curl 中招**。Windows 上 git 与 curl 都走 schannel，
   但 Git for Windows 对吊销失败的容忍度更高：实测 git 2.55 默认就能 clone。
   所以排查时**必须把 git 和 curl 分开实测**，别假设「两个都坏了」。

本项目的做法（三处配合，全自动，无需任何开关）：
  ① gen_certs.py 给服务器证书加
       crlDistributionPoints = http://127.0.0.1:<端口>/ca.crl
     并用 openssl ca -gencrl 生成 certs/ca.crl；
     端口写进 certs/crl-port.txt（默认 18444），反代据此监听 —— 两端不会错位。
  ② gh-proxy.py 在本机该端口起一个**只服务 /ca.crl** 的极小 HTTP 监听。
  ③ schannel 取到 CRL → 吊销检查真正成功 → 放行。

  → curl / git / 任何 schannel 工具都**不需要任何开关**。

实测反证：`file://` 形式的 CRL 分发点 **Windows 链引擎不读**，
吊销状态仍是 UNKNOWN，等于白写。所以只能用 http://。

若该监听因故没起来（端口被占等），反代启动横幅会明确报警，此时回退方案：
  在 %USERPROFILE%\.curlrc 写一行  ssl-revoke-best-effort
  （比 --ssl-no-revoke 好：仍然尝试检查，只是吊销源不可达时不硬失败）

改了证书（重跑 gen_certs.py）之后，必须重启反代才生效。

【已知限制】(2026-09-19 安全审计补充)
------------------------------------------------------------
1. 「无 SNI」回退模式只验证证书链、无法核对主机名。本反代已把可信根证书
   钉扎成白名单（ gh-proxy.py 里 NOSNI_ROOT_PINS，2026-09-19 实测采集），
   链根不在名单内的连接会被拒绝。若 GitHub 更换根证书导致该模式被大面积
   拒绝，可临时把 gh-proxy.py 里 NOSNI_PIN_MODE 改为 "log-only" 应急，
   并按文件内注释重新采集底账。
2. gh-proxy.log 会记录访问过的路径（隐私卫生）：日志只在每次部署时清空，
   卸载不会删除。介意请手动清空或删除该文件。
